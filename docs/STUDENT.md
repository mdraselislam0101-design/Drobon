# Student workflow (Pump 18)

Pump 18 adds a Student-facing entry route, progress/history presentation, and clearer guidance labels over the existing shared security core. Student is not a separate scanner, project, quota, finding, report, or assistant system. The matrix below records each scoped capability and its implementation or explicit limitation.

## Learning path (Phase 22 Pump 2)

Phase 22 Pump 2 adds an internally authored, bounded learning path that turns the existing scan/finding machinery into a LEARN → PRACTICE → VERIFY → TRACK loop. No new engine, dataset, or execution sandbox was introduced.

- **Catalog (4 lessons, server-side answers).** `lsn_code_injection_eval` (DG-SAST-002), `lsn_command_injection_exec` (DG-SAST-001), `lsn_xss_dynamic_html` (DG-SAST-004), `lsn_hardcoded_secrets` (DG-SAST-005). Every lesson carries concept text (which quotes the rule's honest lexical limitations), objectives, a synthetic starter/fixed fixture pair, and a 3-question knowledge check whose answer keys and explanations exist only inside the API process — `GET /api/v1/student/lessons` serializes a projection that structurally cannot contain them (shared guards + API tests).
- **Routes.** `GET /api/v1/student/lessons`, `GET /api/v1/student/progress`, `POST …/lessons/:lessonId/read`, `POST …/lessons/:lessonId/quiz`, `POST …/lessons/:lessonId/practice/IDENTIFY|FIX`. All require authentication, reject any query parameter, and cap bodies (1 KiB). Progress is read from the caller's session only — there is no user parameter to forge.
- **Server-authoritative progress.** A dedicated durable JSON store (`STUDENT_STORE_PATH`, default `.data/student-progress.json`; `:memory:` outside production) keeps per-user, per-lesson state: read acknowledgement (idempotent, earliest timestamp kept), quiz records (server-scored; best score never decreases; 200-attempt cap enforced server-side with an atomic reject), and practice evidence. Persisted unknown lesson ids make the store refuse to start; the document has size/count caps and is written atomically.
- **Verified practice over the real workflow.** IDENTIFY succeeds only when the caller's OWN projects contain a COMPLETED SAST scan with a finding for the lesson's target rule. FIX succeeds only when the existing finding workflow reports `NOT_OBSERVED_IN_LATEST_SCAN` for that finding — i.e. the learner actually applied the fix and re-scanned. The browser can never submit completion; 409 with instructive text is the honest answer until real evidence exists. "Not observed" is not presented as a remediation guarantee.
- **Safety.** Fixtures are clearly labelled synthetic depictions that never execute inside DROBON; the learner runs the ordinary scanner on their own project. No exploit instructions beyond the detected pattern, no CVE/NVD/GHSA/OSV/KEV/EPSS or any external feed, no network calls. The API-name exemption for the lesson-data file in the static-safety gate is compensated by a structural test: the module is pure data (no runtime imports) and the forbidden names occur only inside string literals.
- **Still NOT_IMPLEMENTED.** CTF-style challenges, mentor Q&A, study groups, video tutorials, certification/credential presentation, job board, résumé generator, arbitrary-code playground, notes/bookmarks, CWE encyclopedia navigation, and AI tutoring beyond the shared provider-`NONE` assistant. DG-SAST-003/006 are not yet taught (candidate future lessons).

## Student workflow surface

The dashboard is a bounded progress/history surface based on persisted server state. Project-level source, scan, finding, lifecycle, report and assistant features remain shared with Developers. The Student classification changes workspace presentation only; authentication, role authorization, project ownership, plan entitlement, account/device quota, rate limits and scan lifecycle remain authoritative on the server.

- FREE remains three scans per UTC month per account, with the existing shared-device anti-abuse controls. PRO is available only through the existing server entitlement (`PRO + ACTIVE`).
- Account enabled/disabled state is not modeled. DAST consumes normal scan quota and is not an active crawler. External credential verification is not performed.
- Student explanations, next steps and persisted progress/history use the existing finding and scan workflows. Assignments, grades or classroom/teacher administration are **NOT_IMPLEMENTED** and are not implied by the Student presentation; the Phase 22 lesson catalog is a self-study learning path, not a course with grading. UserType remains classification; the underlying assessment API is governed by project ownership, not a Student-specific or Security-Professional-only privilege.
- Assistant provider state remains `NONE`; deterministic supported answers use authorized saved evidence, and unsupported generation remains unavailable. Pump 19 adds aggregate assessment/verification/DAST question handlers to that shared assistant.
- Shared dashboard scan cards also show a completed DAST observation count and completed SCA assessment/dataset states when those persisted results are available; neither is a security verdict or complete-coverage claim.
- External AEGIS intelligence remains separate. No vulnerability data is loaded or bundled; SCA without it remains `NOT_ASSESSED` / `NO_DATA_LOADED`.
