# Security Professional workflow (Pumps 19 and 22)

Pump 19 added the Security Professional dashboard and login/register destination. Pump 22 adds a structured assessment record to that shared platform: project-bound objectives/scope, lifecycle, user authorization declarations, linked existing scans/findings/remediation/reports, and append-only history. It adds no scanner, duplicate finding/report engine, entitlement, or elevated role. UserType still controls presentation only; the API enforces authenticated project ownership, scan quota/plan, and the existing DAST policy independently.

## Structured assessment workflow (Pump 22)

The project page shows this panel for Security Professional and Pentester presentation, while all assessment API access remains classification-neutral and owner-scoped. The server derives the account from the session, checks project ownership first, and then looks up an assessment only within that account/project. Unknown, malformed, foreign-project and cross-account assessment IDs do not reveal another assessment. Client-supplied owner, status, UserType, plan, target, or project fields are rejected; `assessmentId` on a scan request is validated against the authenticated account and path project.

- Create a `PLANNED` assessment with 1–10 objectives, at most 20 exact DNS hostnames per include/exclude list, and bounded notes. Wildcard, IP-literal, duplicate, overlapping and malformed hostname entries are rejected. Subdomains are not implicitly in scope. Per-project count, JSON document size, event history, declaration history and response summaries are bounded.
- Edit title/objectives/scope only while `PLANNED`. Legal transitions are `PLANNED → ACTIVE → COMPLETED`, with cancellation from `PLANNED` or `ACTIVE`; completed/cancelled records are terminal. Completion needs at least one completed linked scan and no queued/running linked scans. Cancellation also waits for linked scans to stop. Repeating a current status is an idempotent no-op; stale/backward transitions are rejected.
- An optional `assessmentId` on scan creation binds the scan to an assessment only if it is owned by the same account and project and currently `ACTIVE`. A linked DAST target must have its exact configured hostname explicitly in scope and not in the exclusions. Assessment serialization linearizes linked scan creation against close/cancel. Existing scan engines, finding lifecycle, remediation notes, rescan verification and report generation remain the sources of truth; assessment detail summarizes/links rather than cloning those records. Reports preserve the optional scan-to-assessment ID in their immutable scan snapshot.
- For a configured project DAST target whose exact host is included, an active assessment owner can append a `USER_DECLARED` statement or withdraw it. The declaration stores the exact configured URL and timestamp and appends history; the account/project association is the assessment record's server-held owner/project. It does not collect or validate legal documents or prove third-party permission. `UNVERIFIED` is the honest state when no current exact-URL declaration exists. DAST can be linked without a declaration and remains subject to the ordinary project target safety/DNS/SSRF/redirect/request policy.
- Persistence uses the existing atomic, mode-0600, restart-safe JSON-store architecture (`ASSESSMENT_STORE_PATH`, default `.data/assessments.json`; `:memory:` is rejected in production). The store is a bounded single-process/single-writer foundation, not a new production database.

API and UI evidence: `apps/api/test/assessmentsApi.test.ts`, `apps/web/test/assessmentUi.test.tsx`, `packages/shared/test/assessments.test.ts`, and `apps/api/test/config.test.ts`. The HTTP test uses synthetic local DAST DNS/transport fixtures only. UI tests are component tests, not browser E2E.

## Regression comparison and engagement summary (Phase 22 Pump 3)

Pump 3 adds two bounded professional-workflow surfaces on the existing engines. Neither introduces a second finding engine, a correlation guess, a score, or a dataset.

- **Scan regression comparison** — `GET /api/v1/projects/:projectId/scans/:scanId/compare/:baselineScanId` compares two COMPLETED scans of the same type within the same owned project by finding fingerprint. States are honest: `NEW` (observed now, absent from baseline), `UNCHANGED` (observed in both, same rule-fixed severity), `CHANGED` (observed in both, different severity), `RESOLVED` (observed in the baseline, **not observed** in the comparison scan — the same evidence class as `NOT_OBSERVED_IN_LATEST_SCAN`: retest evidence, never proof of repair), and `REOPENED` (observed in both while the persisted finding workflow is currently `REOPENED`). No historical workflow state is invented; foreign/malformed/unknown ids all answer the same uniform 404; the route has no query surface. The project page exposes a per-scan "Regression compare" control rendering the counts and entries.
- **Assessment engagement summary** — `GET /api/v1/projects/:projectId/assessments/:assessmentId/summary` aggregates an assessment's OWN linked scans: per-scan status/severity lines, report availability, and totals. It summarizes persisted records only: it never invents history, never presents a security score or cross-scan deduplication, and surfaces `partial` sweeps so totals are never read as complete coverage. Dependency intelligence remains `NOT ASSESSED` / `NO DATA LOADED` in all summaries. The assessment panel exposes a "Load engagement summary" control.
- **Safety and regressions.** Both routes are owner-scoped and fail closed (401 anonymous, 403 cross-account, 422 malformed/same-scan, 404 probing, 409 type/incomplete mismatch). FREE remains three scans per account per UTC month and the probe verified a live fourth-scan denial plus UserType-switch neutrality; the passive-DAST policy refused loopback, private (RFC 1918), link-local/metadata and malformed targets live (422). SARIF/SBOM/report exports, the FALSE_POSITIVE lifecycle and the Student learning path remain fully green.

## Overview semantics

The dashboard uses the same authenticated `GET /api/v1/me/security-overview`, subscription, and usage endpoints as the existing account workspaces. Its fixed-cap recent activity is history, not complete coverage. Scan cards contain only persisted summary metadata: findings total, partial-result flag, persisted-report availability, completed DAST observation count, and SCA assessment/dataset state. Detailed evidence and scan results stay in the authorized project workflow.

- Dashboard finding severity, lifecycle and verification summaries describe persisted latest observations per unique finding identity; they are not a global security score or remediation certification.
- DAST observations describe a small bounded passive request set. They do not imply route discovery, browser behavior, full application coverage, or vulnerability absence.
- SCA inventory is separate from vulnerability intelligence. No dataset/provider remains `NOT_ASSESSED` / `NO_DATA_LOADED`; that is never displayed as zero vulnerabilities.
- `SECURITY_PROFESSIONAL` changes navigation and overview presentation only. Role-based admin capability remains governed by the account role; UserType never grants or suppresses authority.

## Assistant scope and safety

The assistant remains deterministic, read-only and project-scoped. With provider state `NONE`, supported questions use saved records only; unsupported/open-ended requests remain unavailable. Assessment and DAST summaries use the latest completed scan per available engine. Project-wide unresolved/verification/attention questions reuse the existing persisted summary query with a server-derived project filter, so a finding absent from the newest scan can still retain its latest verification state. An explicit scan ID narrows these workflow answers to that authorized scan and its bounded finding details.

DAST answers report only persisted observation counts/status summaries and say that these are not vulnerability verdicts. Lifecycle `RESOLVED` remains user-managed; `NOT_OBSERVED_IN_LATEST_SCAN` is not proof of remediation. Missing details, partial/truncated results and incomplete workflow records are disclosed. Project/source/finding/DAST text remains untrusted data; it is not executed as instructions. No LLM output, source edits, arbitrary networking, external credential verification, or new scan action is added.

## FREE/PRO and security boundaries

- FREE remains three scans per UTC month under the existing account/device policy. PRO quota exemption comes only from the server subscription/entitlement authority.
- UserType, role, plan, entitlement, owner and resource IDs supplied by a client are not trusted. The API checks session identity, project ownership and supported request shape.
- The Professional UI uses existing workflows and contracts. It adds no Admin or payment-review controls.
- DAST remains one configured target with the existing SSRF, DNS, redirect, transport and request-bound protections; tests use synthetic local fixtures.
- No PostgreSQL, production database, vulnerability/security data feed, bundled catalog, fabricated evidence/score/finding, or external secret verification is introduced.
- Account enabled/disabled state is not modeled.
- An assessment scope or user declaration is never role, project, plan, quota, target-network, or scan permission; UserType is not consulted for API authority.
