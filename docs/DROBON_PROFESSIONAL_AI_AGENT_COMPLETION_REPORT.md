**তারিখ:** ২০২৬-১০-৩১

**সিদ্ধান্ত: PARTIALLY IMPLEMENTED; STORAGE BLOCKER; PRODUCTION NO-GO**

এটি বিদ্যমান Main App-এর ভিতরে তৈরি একটি সীমিত **deterministic security coordinator**। এটি কোনো AI model চালায় না, স্বাধীনভাবে exploit প্রমাণ করে না এবং XBOW, NodeZero বা Pentera-এর সমপর্যায়ের দাবি করে না। বাস্তব অগ্রগতি ও গুরুত্বপূর্ণ অসম্পূর্ণতা নিচে আলাদা করে দেওয়া হলো।

## Master Prompt পুনঃনিরীক্ষা — Phase A শেষ, Phase B-তে STORAGE BLOCKER

**বর্তমান সিদ্ধান্ত: STORAGE BLOCKER; PRODUCTION NO-GO।** নিচের UID পরীক্ষায় নির্দিষ্ট synthetic অবস্থায় Linux kernel-এর বাধা প্রমাণিত হয়েছে, কিন্তু Main App সেই identity, directory, ancestor ও writer retirement বাধ্যতামূলকভাবে provision বা enforce করে না। একই host UID-তে পুরোনো writer এখনও v2 নষ্ট করতে পারে। তাই এই নতুন পরীক্ষা কোনো product fix নয়; শুধু পরীক্ষার script ও এই প্রতিবেদন যোগ/আপডেট করা হয়েছে। Agent default-off ও production-এ নিষিদ্ধ রয়েছে।

### B. Mandatory OS boundary — পৃথক-process adversarial পরীক্ষা, product integration এখনও নেই

`scripts/verify-agent-os-boundary.mjs` temporary synthetic file-এ pinned পুরোনো scan-store **source** ও বর্তমান scan-store/shared **source** local `esbuild` দিয়ে bundle করে। পুরোনো writer v1 memory-তে নেওয়ার পর synthetic v2 প্রকাশ হয়। Linux/ext4 sandbox-এ বর্তমান host UID 1001; আলাদা process-এর UID 65534 (`nobody`) `sudo -n` দিয়ে চালানো হয়। কোনো scanner বা Dataset চালানো হয় না। Script-এর এই identity ও `unshare -Ur` সুবিধা না থাকলে স্পষ্টভাবে fail/block করবে, silently skip করবে না। এটি পুরোনো পূর্ণ API binary বা production deployment test নয়।

Reproduce: `node scripts/verify-agent-os-boundary.mjs` (Linux, স্থানীয় dependencies, pinned commit, `unshare -Ur`, executable `sudo -n -u nobody` প্রয়োজন); exit ০ মানে **উপরের expected success ও expected failure দুটোই পুনরুৎপাদিত**, production isolation পাস নয়। `node scripts/verify-agent-server-coexistence.mjs` আবারও opaque injection-সহ pinned পুরোনো source API এবং আগের locally-built বর্তমান API-র একই-UID data loss পুনরুৎপাদন করেছে। প্রথম UID-test draft-এ সফল আক্রমণের পর `0600` file-এর মালিক `nobody` হওয়ায় parent-এর test read `EACCES` পেয়েছিল; harness পরে ওই child দিয়ে synthetic result পড়েছে—কোনো permission শিথিল বা আগের security test বদলানো হয়নি।

**কেন blocker রয়ে গেছে:** App কোনো নিশ্চিত নতুন dedicated UID তৈরি/বাধ্যতামূলক করে না, সব পুরোনো process ও একই UID-র writer শনাক্ত/অপসারণ করে না, protected ancestor/mount/ACL/hard-link/alias ও inherited open-file inventory যাচাই করে না, opaque custom store ও direct user-কে OS boundary-র ভিতর নিয়ে আসে না, বা অন্য host/namespace-এ authority নিশ্চিত করে না। Root, `CAP_DAC_OVERRIDE`, একই service UID বা trusted executable/config পরিবর্তন করতে পারে এমন actor-কে `0700` ঠেকায় না। এই sandbox-এর বর্তমান user non-interactive sudo করতে পারে এবং `/usr/local/bin/node` ও তার directory writable mode-এ আছে; আক্রমণ না চালিয়েও এটি পূর্ণ host-hardening প্রমাণের অভাব দেখায়। কোনো host binary বা permission পরিবর্তন করা হয়নি।

**প্রয়োজনীয় পরবর্তী নকশা, এখনও NOT IMPLEMENTED:** একটিমাত্র বর্তমান API deployment-এর জন্য আলাদা non-privileged service identity ও root/authority-controlled trusted path provision করা; আগে থেকে চালু legacy ও সমপরিচয়ের সব writer থামানো/বিচ্ছিন্ন করা; fresh inode-সহ নির্দিষ্ট protected storage-এ কেবল অনুমোদিত identity-র access রাখা; binary, config, dependencies, ancestors, ACL, capabilities, backups, mount/namespace ও অন্য host রক্ষা করা; অজ্ঞাত injected/direct store fail closed করা। প্রকৃত প্রশাসনিক cutover, identity provisioning বা migration এই phase-এ করা হয়নি, এবং কেবল configuration দাবি বা advisory check দিয়ে এই gate বন্ধ হবে না।

### Phase অগ্রগতি ও এই turn-এর যাচাই

- **A — repository audit:** করা হয়েছে; actual deployment inventory **NOT TESTED**। শুরুতে ২৪ tracked modified ও ২২ untracked path-এর ৪৬টির private `/tmp` backup ও hash inventory নেওয়া হয়েছে।
- **B — mandatory isolation:** Linux synthetic OS case **PARTIALLY VERIFIED**, Main App-এ mandatory provisioning/enforcement **NOT IMPLEMENTED / BLOCKED**। সংশ্লিষ্ট storage/lease/crash/quota পরীক্ষায় **৯ file / ৫৭ pass, ০ fail, ০ skip**; script-এর targeted ESLint **PASS**। বিদ্যমান full-server loss rehearsal exit ০ দিয়ে ক্ষতি পুনরায় দেখিয়েছে।
- **C — বাস্তব migration/cutover/rollback implementation:** **NOT IMPLEMENTED / NOT RUN** এই turn-এ; আগের copy-only rehearsal-কে পূর্ণ migration বা rollback ধরা যাবে না।
- **D–F — নতুন withdrawal/worker, model এবং Agent/scanner কাজ:** নির্দেশিত ক্রমে B blocker অমীমাংসিত থাকায় এই turn-এ এগোনো হয়নি। নিচের আগের ফল ঐতিহাসিক প্রমাণ; distributed propagation, প্রকৃত model ও independent validation এখনও খোলা।
- **G — নতুন সম্পূর্ণ regression, typecheck, পূর্ণ lint/build ও benchmark:** এই turn-এ **NOT RUN**, কারণ critical Phase B বন্ধ হয়নি। আগের ১,৮৭১ pass/১ skipped পূর্ণ run নিচে পৃথকভাবে আছে; তাকে এই turn-এর ফল বলা যাবে না। Phase B পরিবর্তনের safety check হিসেবে offline secret (৯০৭ file), self-test, boundaries, repository integrity ও release-evidence self-test **PASS**; networked audit চালানো হয়নি।
- **H — এই প্রতিবেদন:** আপডেট করা হয়েছে। কোনো Dataset/production/VPS data পড়া, মাইগ্রেট, বদল বা deploy হয়নি।

## আগের writer-isolation ও worker audit — স্থায়ী সমাধান এখনও অসম্পূর্ণ

**গুরুত্বপূর্ণ সিদ্ধান্ত:** Agent execution default-off এবং production-এ নিষিদ্ধই আছে। Equal directory write/rename permission-সহ আগে থেকে চালু পুরোনো process নতুন lock, version বা hash check মানতে বাধ্য নয়। তাই শুধু application code দিয়ে ওই process-কে স্থায়ীভাবে থামানো যায়নি; নিয়ন্ত্রিত cutover ও OS/storage-এ বাস্তব write-permission বিচ্ছিন্নতা ছাড়া **NO-GO**। নিচের passing পরীক্ষাগুলোর একটি পুরোনো writer দিয়ে ইচ্ছাকৃত data loss পুনরুত্পাদন করে; test pass মানে ঝুঁকিটি সমাধান হয়েছে নয়।

**মূল সীমা:** নতুন writer-এর `check` ও `rename` আলাদা syscall; noncooperating writer মাঝখানে লিখতে পারে। Linux abstract socket একই network namespace-এর সহযোগী server-এ সীমিত; per-file lock-ও advisory। শুধু প্রক্রিয়ার UID/ACL/path isolation, পুরোনো সব writer বন্ধ/বিচ্ছিন্ন এবং স্বাধীন পরীক্ষায় প্রমাণিত authoritative transactional storage/cutover-ই দীর্ঘমেয়াদি boundary দিতে পারে। এগুলোর কোনোটিই এখানে production-এ প্রয়োগ বা অনুমোদিত হয়নি। নতুন process-এ আগের file সম্পূর্ণ অনুপস্থিত থাকলে তা নতুন path-এর সঙ্গে পৃথক করার durable manifest নেই—synthetic test-এ খালি store দেখা যায়; এটি recovery success নয়।

### Deterministic বনাম প্রকৃত AI reasoning

বর্তমানে scanner বাছাই/queue, policy checks, bounded JS/TS syntax count, source/response-location মিল, severity থেকে priority এবং same-file pair—সবই নির্দিষ্ট নিয়মে চলে। User objective বুঝে নতুন hypothesis গঠন, পরিস্থিতি অনুযায়ী স্বতন্ত্র tool-selection ও multi-step যুক্তি, ভুল finding-কে কারণসহ challenge এবং স্বাধীনভাবে vulnerability/exploit যাচাই করার কোনো AI reasoning বা model নেই। ভবিষ্যতে এগুলোকে সত্যিকারের AI capability বলতে হলে প্রকৃত reasoning integration এবং স্বতন্ত্র পরীক্ষা প্রয়োজন; সব security validation যে AI দিয়েই করতে হবে এমন নয়। Model যোগ করলেও exploit প্রমাণ স্বয়ংক্রিয়ভাবে মেলে না: স্বতন্ত্র evidence, নিরাপদ sandbox, scope/approval, prompt-injection প্রতিরোধ এবং human review লাগবে। এই ধাপে এমন কোনো advanced feature যোগ করা হয়নি।

স্থানীয় runtime খোঁজে `ollama`, `llama`, `llama-cli`, `llama-server`, `llamafile`, `nvidia-smi`, `rocm-smi` পাওয়া যায়নি। Python-এ `torch`, `transformers`, `llama_cpp`, `onnxruntime`, `sentence_transformers`, `tensorflow`, `ctransformers`, `mlx`, `vllm`; Node-এ `onnxruntime-node`, `@huggingface/transformers`, `node-llama-cpp` পাওয়া যায়নি। Main App workspace-এর সর্বোচ্চ পাঁচ স্তরে, dependency/build বাদ দিয়ে, `.gguf`, `.ggml`, `.safetensors`, `.onnx` model file পাওয়া যায়নি। এটি পুরো host বা সব সম্ভাব্য model-এর exhaustive inventory নয়। কোনো model ডাউনলোড বা external AI call করা হয়নি। প্রকৃত model reasoning যোগ করতে অনুমোদিত local runtime ও model weights, সম্পদ/লাইসেন্স, নিরাপদ tool/egress design, prompt-injection ও human-review controls এবং স্বাধীন benchmark প্রয়োজন; এগুলো এই পরীক্ষায় নেই।

### প্রকৃত local model-এর সর্বনিম্ন ভবিষ্যৎ নকশা — প্রস্তাব, বাস্তবায়ন নয়

1. বিদ্যমান `AssistantProvider` boundary-ই ব্যবহার; অনুমোদিত, লাইসেন্স-যাচাই করা local model/runtime ও pinned weights না থাকলে `NONE`/`UNAVAILABLE` থাকবে। এই audit-এ model, runtime বা weights ইনস্টল/ডাউনলোড করা হয়নি; কোনো external AI API, paid service বা security engine ব্যবহৃত হয়নি। সাম্প্রতিক পুনঃপরীক্ষায় `ollama`, `llama-server`, `llama-cli`, `nvidia-smi`, `rocm-smi`; Python-এর `torch`, `transformers`, `llama_cpp`, `onnxruntime`, `vllm`, `mlx`; এবং পরীক্ষিত npm model package পাওয়া যায়নি। `/home/user`-এর সর্বোচ্চ পাঁচ স্তরে খোঁজা `.gguf`, `.safetensors`, `.onnx`-ও মেলেনি; এটি machine-wide exhaustive inventory নয়।
2. ভবিষ্যতে আলাদা সীমিত OS identity ও egress-denied sandbox-এ কেবল operator-provisioned read-only weights; bounded CPU/RAM/time এবং স্থানীয় অনুমোদিত IPC। Model-এর shell, scanner, filesystem write বা network access নয়। বাস্তব deployment-এ isolation অবশ্যই যাচাইযোগ্য হতে হবে; নামমাত্র prompt নির্দেশনা নিরাপত্তা boundary নয়।
3. বিদ্যমান auth/tenant/scope ও redaction-এর পরে সীমিত evidence reference, scanner coverage ও uncertainty পৃথক untrusted data হিসেবে দেওয়া; raw secrets বা পুরো source default-এ নয়। Model output closed schema ও বিদ্যমান evidence ID দিয়ে যাচাই; নতুন অনুমোদন, target বা tool action তৈরি করতে পারবে না। Prompt injection ও secret redaction পরীক্ষার প্রমাণ ছাড়া enabled নয়।
4. Model-produced ব্যাখ্যা/পরিকল্পনা কেবল **hypothesis**, scanner alert আলাদা এবং exploit/vulnerability `VALIDATED` কেবল স্বাধীন reproducible evidence ও অনুমোদিত human review-এ। Model confidence নিজে validation নয়। বাস্তব model benchmark, multi-tenant isolation, adversarial prompt, নিরাপত্তা, privacy ও অপারেশনাল পরিমাপের পরে আলাদা approval লাগবে।

**Finding শ্রেণির সীমা:** বর্তমান output বিদ্যমান scanner-এর alert; location বা response-এর structural মিল কেবল সীমিত evidence, vulnerability প্রমাণ নয়। `INCONCLUSIVE`/`NOT_VERIFIED` মানে অনিশ্চিত, নিরাপদ নয়। Model নেই বলে AI hypothesis নেই; independently evidence-supported vulnerability, স্বাধীনভাবে validated vulnerability, exploitability proof এবং false-positive নির্ণয় কোনোটিই এখানে দাবি করা হয় না।

## ৩. সীমিত local/test workflow ও UI ব্যবহার

**Production-এ চালাবেন না।** Default-এ agent কাজ তৈরি করে না। শুধু স্পষ্ট local/test opt-in এবং অন্য কোনো environment থেকে সম্পূর্ণ বিচ্ছিন্ন, পরীক্ষার পরে ফেলা যাবে এমন store-এ নিচের workflow পরীক্ষা করা যায়। পুরোনো binary-এর সঙ্গে এ ধরনের store ভাগ করা যাবে না। Production config-এ opt-in প্রত্যাখ্যাত হয়; কোনো approval override বর্তমানে নেই। Environment ভুল করে production-এর বদলে development বলা হলে এই শনাক্তকরণ নিজে থেকে বাস্তব deployment চিনতে পারে না—operator/deployment isolation অপরিহার্য।

1. নিজের project-এ source snapshot ও প্রয়োজন হলে নিরাপদ DAST target রাখুন। Security Professional/Pentester presentation-এ assessment তৈরি করে exact host scope ও উদ্দেশ্য দিন, তারপর ACTIVE করুন।
2. UI-তে **Record scoped engagement** খুলে প্রকৃত client/owner, অনুমোদিত path prefix, scanner type, স্থানীয় সময়-সীমা ও লিখিত authorization statement দিন; সব অপশন ব্যবহারকারীকে নিজে নির্বাচন ও নিশ্চিত করতে হয়। `/` মানে পুরো host-এর সব path; subdomain নিজে থেকে অন্তর্ভুক্ত নয়। Server আবার validate করে। এটি user attestation, legal authorization যাচাই নয়।
3. **Load agent plan**-এ READY/BLOCKED কারণ ও bounded inventory দেখুন। Configured Dataset-এর বর্তমান availability execute-এর সময় পুনরায় যাচাই হয়। Queue করার আগে আলাদা checkbox-এ নিশ্চিত করুন; existing scan quota প্রযোজ্য।
4. Queue হলে বিদ্যমান scan history refresh হয় এবং active task-এ agent panel poll করে। আংশিক scanner coverage, queue outcome অনিশ্চিত হলে `INCONCLUSIVE`, এবং job `FAILED` হলে সেটি দেখানো হয়; retry-এর আগে saved job ও quota পরীক্ষা করা প্রয়োজন।
5. Finding review-তে `SUSPECTED` মানে কেবল সংরক্ষিত source location বা response-এর structural মিল, exploit প্রমাণ নয়। `INCONCLUSIVE`/`NOT_VERIFIED` নিরাপদ ফল নয়। Same-file pair বাস্তব attack path নয়। বিদ্যমান scan-এ evidence ও remediation খুলুন; customer নিজে পরিবর্তন ও অনুমোদিত rescan করবেন।
6. Agent panel-এর JSON export শুধু bounded public summary; raw source বা নতুন exploit evidence নয়। Scanner reports আলাদা করে বিদ্যমান workflow থেকে generate/download করতে হয়।
7. `QUEUED`/`RUNNING` Agent task-এ **Cancel ... job** এবং পরের আলাদা confirmation দিলে cancellation intent durable হয়। `CANCELLING` মানে worker এখনও terminal transition করেনি; `CANCELLED` মানে job terminal failed, scanner result সংরক্ষিত হয়নি—কিন্তু আগে পাঠানো bytes ফেরত আনা যায় না এবং abort না-মানা transport/engine পেছনে চলতে পারে। Cancellation quota ফেরত দেয় না। Active linked job থাকলে পুরো assessment cancellation আগের মতো 409; job settle হওয়ার পর আবার চেষ্টা করতে হয়।
8. Engagement withdraw হলে তার সঙ্গে বাঁধা running Agent job-এ abort signal যায় এবং queued job সেই একই engagement পুনরায় যাচাই করে fail হয়; অন্য active engagement নিজে থেকে পুরোনো job-কে reauthorize করে না। শুরু-হওয়া HTTP request ফেরত আনা যায় না। Synchronization কেবল একই cooperating process-এর জন্য, distributed kill নয়।

API: authenticated `GET /api/v1/projects/:projectId/assessments/:assessmentId/agent`, `POST .../agent/execute` এবং `POST .../agent/scans/:scanId/cancel`, উভয় POST-এ strict `{ "confirm": true }`। Cancel অনুরোধ চলমান/queued job-এর জন্য 202 `CANCELLING`, আগেই cancel হয়ে terminal হলে 200 `CANCELLED`; অন্য terminal job-এ 409। Safety action হিসেবে execution disabled থাকলেও cancel অনুমোদিত। Owner ও অন্যান্য policy server-side; UI-এর user-type presentation নিজে নিরাপত্তা boundary নয়। বিদ্যমান scan endpoint private agent metadata গ্রহণ বা প্রকাশ করে না। নতুন Agent-state enum পুরোনো strict Agent client-এ অজানা হতে পারে; তা upgrade করা দরকার।

## ৪. Synthetic actual-agent benchmark

পুনরুৎপাদন (কোনো external target নয়):

```bash
npm run build --workspace @drobon/shared
npm run test --workspace @drobon/api -- test/agentApi.test.ts -t 'synthetic agent benchmark'
```

Test-এর মধ্যেই নিজস্ব synthetic rules/catalog, uploaded files ও in-memory DAST transport তৈরি হয়; এগুলো Drobon-Dataset নয়। দুইবার positive এবং দুইবার negative project run: মোট ১৬টি rule-match observation। একটিমাত্র condition-ভিত্তিক rule প্রতিটি scanner-এ; generated finding-এর rule ID-র বিপরীতে oracle। Positive finding থাকলে TP, negative finding থাকলে FP; finding না থাকলে কেবল `COMPLETED` task-এর জন্য TN/FN। PARTIAL/FAILED/BLOCKED-এ finding না থাকলে `UNASSESSED`, কখনও pass নয়। Runtime exploitability আলাদা প্রশ্ন; একই positive SAST-এর দুই repetition `UNKNOWN`।

|---|---:|
| TP / FP / TN / FN | 8 / 0 / 4 / 0 |

চারটি run-এর harness শেষ হওয়া মানে সব scanner-এর coverage complete নয়—SAST ও SCA `PARTIAL` ছিল। এই 1.0 মান চারটি হাতে তৈরি সাধারণ rule-এর ক্ষুদ্র পুনরাবৃত্তি; real-world accuracy, vulnerability truth, exploit reproducibility, vendor তুলনা বা independent review-এর মাপ নয়। Repetition-গুলো independent dataset নয়। Evidence-field উপস্থিতি evidence-এর সত্যতা বা exploit completeness নয়। Unassessed, blocked ও unknown-কে precision/recall denominator-এ pass হিসেবে ঢোকানো হয়নি। অন্য real target scan করা হয়নি।

**Lifecycle ও security-র নির্দিষ্ট প্রমাণ:**

- Queued ৪টি agent job JSON store বন্ধ/খুলে পাওয়া যায়; আগের `RUNNING` job restart-এ `SCAN_INTERRUPTED` হয় এবং বাকি queued job চলে। Restart-এর সময় flag disabled হলে ৪টিই transport-এর আগে fail করে। একই assessment/scanner-এর concurrent বা পুনরাবৃত্ত single-process অনুরোধ ও পরীক্ষিত reopen-এ duplicate job হয় না; distributed guarantee নয়।
- Active linked job থাকা পুরো assessment cancel করতে গেলে আগের মতো **409**। নতুন per-job API-তে explicit confirmation, owner/project/assessment check, durable intent এবং queued/running recovery পরীক্ষা হয়েছে। Cancelled queued job-এ scanner probe **0**; একটি SAST job cancel করলেও অন্য তিন scanner স্বাধীনভাবে শেষ হয়েছে এবং quota refund হয়নি। Cancel ও completion একই scan mutation queue-তে ক্রমানুসারে নির্ধারিত; withdrawal ও result commit assessment lock-এ নির্ধারিত।
- Withdrawal/cancellation ঠিক probe-start-এর আগে commit হলে transport call **0** হওয়ার controlled interleaving পরীক্ষা আছে। ঠিক আগে authorization ও cancellation একত্রে পরীক্ষা করে assessment→scan lock-এর মধ্যে শুধু synchronous transport start করা হয়; network promise lock ধরে অপেক্ষা করে না। দুইটি বাস্তব Node HTTP transport পরীক্ষায় শুধু test-owned loopback listener-এ (test-only transport adapter দিয়ে) একটি করে request পৌঁছায়, তারপর cancellation/withdrawal-এ socket বন্ধ হয়। Production target policy বদলানো হয়নি। ইতিমধ্যে পাঠানো request ফিরিয়ে আনা যায় না। Abort উপেক্ষাকারী fake transport terminal job-এর পরও চলতে পারে, কিন্তু তার response/redirect আর গ্রহণ করা হয় না।
- একই process-এর পরপর দুবার queue failure inject করা হয়েছে: একটি সংরক্ষণের আগে, অন্যটি সংরক্ষণের **পরে**। দ্বিতীয় ক্ষেত্রে outcome `INCONCLUSIVE`, পরের scanner চেষ্টা বন্ধ; স্থিতিশীল retry-তে আগে সংরক্ষিত job-গুলো দ্বিগুণ হয়নি এবং FREE quota ৩-এর বেশি চার্জ হয়নি। এটি সব crash/ambiguous cross-file transaction বা cross-process retry-এর প্রমাণ নয়; durable uncertainty barrier নেই। প্রথম test draft-এ action list-এ আগের job দেখানোর ভুল প্রত্যাশায় ১টি test fail হয়েছিল; বর্তমান API READY candidate থাকলে actions-এ কেবল candidate দেখায়, আগের job ফিরে আসা plan-এ থাকে। Assertion সংশোধনের পর সংশ্লিষ্ট run ১১৮/১১৮ pass; আরও তিনটি test যোগের পর উপরের ১২১/১২১ pass; production code বদলানো হয়নি।

## ৬. নিরাপত্তা ও production blocker

- **Rollback/data compatibility: PARTIALLY MITIGATED, production এখনও BLOCKED।** আগে v1 JSON-এ optional `agent` metadata লিখলে পুরোনো parser সেটি উপেক্ষা করে পুরো store rewrite-এ দুটি synthetic job-এর metadata মুছে দিতে পারত; এর একটি queued থাকলে নতুন code সেটিকে legacy হিসেবে পড়ত। এখন সত্যিকার নতুন Agent-bearing store v2 লেখে, পরীক্ষিত পুরোনো parser v2 প্রত্যাখ্যান করে; বিদ্যমান v1 স্বয়ংক্রিয়ভাবে upgrade হয় না এবং এতে Agent job ও quota charge আটকায়। বর্তমান reader v1-এ `agent` property বা অজানা version পেলে byte না বদলে start বন্ধ করে। কোনো পূর্বে মুছে যাওয়া metadata ওই file থেকে নির্ভরযোগ্যভাবে পুনর্গঠন সম্ভব নয়। v2 header ইতিমধ্যে memory-তে v1 ধরে রাখা পুরোনো writer বা অন্য host/namespace/direct writer-কে file overwrite করা থেকে আটকায় না; বহিরাগত writer isolation ও পৃথকভাবে অনুমোদিত, পরীক্ষিত migration/reconciliation ছাড়া নিরাপদ downgrade দাবি করা যায় না। পুরোনো parser replay-তে কোনো পূর্ণ server বা DAST engine চালানো হয়নি।
- `AGENT_EXPERIMENTAL_ENABLED=false` default; `NODE_ENV=production`-এ `true` হলে config error। Plan, queue creation ও executor-এও disabled/production check আছে, এমনকি পরীক্ষায় সরাসরি injected production config-ও job/probe আটকায়। Config process startup-এ স্থির হয়; চলমান process-এর environment বদলালেই এটি live kill switch নয়। Disabled অবস্থায় restart হলে যেসব queued job-এর agent metadata অক্ষত আছে সেগুলি **FAILED** হয়, pause হয় না। Production-এ চালাতে explicit approval-এর পাশাপাশি নতুন নিরাপদ design ও পরীক্ষা অবশ্যই দরকার; code-এ এখন approval override নেই। সঠিক environment label ও deployment access controls operator-এর দায়িত্ব। এই gate আগের binary-কে বদলায় না এবং বাস্তব downgrade-কে নিরাপদ করে না।
- Dataset digest মূল `packs` ও `vuln-intel` JSON-এর bounded change detector; signature নয়, mutable tree-এর atomic snapshot নয়, external advisory path আলাদা। বড় বাস্তব Dataset-এর agent-mode latency, read-only mount এবং ৩০-সেকেন্ড worker deadline এখানে যাচাই হয়নি। ইন-ফ্লাইট race সম্পূর্ণ দূর করা যায় না।
- Existing legacy Dataset service cache এবং opt-in `DAST_REQUIRE_ENGAGEMENT` সীমা এই agent slice দিয়ে globally সমাধান করা হয়নি। Passive GET-ও side effect করতে পারে; authorization হলো operator statement, আইনগত যাচাই নয়। Existing target safety policy egress সীমিত করে; OS/network sandbox বা distributed egress policy প্রমাণ করা হয়নি।
- JSON socket lease এক Linux namespace-এর সহযোগী server ও পরিচিত direct-injected scan/assessment file-store-এ সীমিত; opaque wrapped/third-party store, multi-host, path alias, noncooperating writer ও network partition সমাধান নয়। Scan/assessment temp-file fsync আছে, directory fsync বা multi-file transaction নেই; crash-এর orphan lock automatic cleanup হয় না। Active-controller registry process-local, cross-host signal নয়। Quota reconciliation restart-নির্ভর। Abort অমান্যকারী callback timeout পেরিয়েও চলতে পারে; CPU-bound কাজ event loop আটকে দিলে request/signal দেরি হতে পারে। SAST/SCA/Secrets in-flight abort latency আলাদাভাবে benchmark হয়নি।
- Source ও ঐতিহাসিক evidence existing store-এ encrypted at rest নয়; বিভিন্ন অজানা secret shape-এর পূর্ণ redaction প্রমাণিত নয়। এই কাজ ঐতিহাসিক data পরিষ্কার/পরিবর্তন করেনি। Agent UI-তে উদ্দেশ্য ও source text instruction হিসেবে model-এ পাঠানো হয় না, কারণ model নেই; এটি ভবিষ্যৎ model prompt-injection নিরাপত্তার প্রমাণ নয়।
- একবার scanner attempt হলে একই assessment-এ retry নেই, নতুন assessment লাগে। Runtime authorization বা Dataset বদলে partial/failed কাজের পুনরায় পরিকল্পনা, distributed cancellation ও পুনরাবৃত্ত reliability test এখনও প্রয়োজন। Consolidated agent report/PDF, fix verification এবং independent human review বাকি।

## ৭. Database/JSON migration ও rollback পরিকল্পনা — **শুধু synthetic copy rehearsal; বাস্তবে চালানো হয়নি**

**Scope ও সিদ্ধান্ত:** Main App-এর পুরোনো scan storage v1 JSON; নতুন Agent-bearing disposable store v2, অন্য legacy store v1-ই থাকে। Current writer-দের স্থানীয় সহযোগী guard আছে, কিন্তু distributed বা পুরোনো writer-এর mandatory fencing নেই; আলাদা Drobon-Database-এর schema/engine এই কাজের জন্য পরীক্ষা বা পরিবর্তন করা হয়নি। তাই নিচে নির্দিষ্ট SQL বা কোনো database capability ধরে নেওয়া হচ্ছে না। Synthetic copy-only পরীক্ষা ছাড়া কোনো production data read, backup, restore, migration, rollback বা database change করা হয়নি। আগে data owner, security, operations এবং ব্যবহারকারীর লিখিত approval ছাড়া কোনো বাস্তব পদক্ষেপ নয়। শুধু অনুমোদন বর্তমান production gate খুলে দেয় না।

1. **Inventory, freeze ও quarantine:** approved operator কোন application version, সব API/worker/cron/backup writer, সব host/namespace, storage path/database, access identity ও dependency আছে তা তালিকাভুক্ত করবেন। Agent default-off রাখবেন; নতুন intake বন্ধ, in-flight request শেষ বা নিরাপদভাবে নিষ্ক্রিয়, সব পুরোনো ও নতুন writer পুরোপুরি থামিয়ে নিশ্চিত করবেন। বর্তমান lease distributed lock নয়; শুধু lock ধরে একাধিক host নিরাপদ ভাবা যাবে না। Pending/running jobs ও quota reservations-কে অনুমতি ছাড়া delete, legacy হিসেবে চালানো বা অন্ধভাবে reset করা যাবে না।
2. **Consistent protected backup:** coordinated freeze-এ authentication/project/assessment/engagement, scan/job/finding/workflow/report, source, usage/quota reservation এবং সংশ্লিষ্ট reference ও access metadata-সহ যেসব store বাস্তবে যুক্ত, তাদের common point-in-time backup নিন। প্রকৃত topology/DB engine যাচাই করে উপযুক্ত backup পদ্ধতি বাছুন; multi-file atomicity ধরে নেওয়া যাবে না। Encrypted, access-controlled, আলাদা immutable কপি, retention/restore permission ও audit রাখুন; source বা secret রিপোর্টে ছাপবেন না।
3. **Restore rehearsal ও baseline:** backup থেকে সম্পূর্ণ বিচ্ছিন্ন test copy-তে restore করে file hash/canonical record digest, record count ও ID-set মিলিয়ে যাচাই করুন। Owner→project→assessment/engagement→scan, source snapshot, findings/workflows, report content digest, quota/reservation, timestamps ও statuses-এর referential integrity যাচাই করুন; discrepancy হলে থামুন। এ rehearsal production backup ব্যবহার করলেও তা শুধু আলাদা সুরক্ষিত পরিবেশে, অনুমোদিত operator করবেন।
4. **নকশা ও dry-run (পূর্ণ migration এখনও তৈরি নয়):** v2 fail-closed JSON reader/writer ও পরীক্ষিত পুরোনো parser rejection আছে, কিন্তু তা running পুরোনো process বা অন্য writer-কে external isolation ছাড়া আটকায় না। পুরোনো সব record ও private Agent metadata losslessly preserve/identify করে reviewed forward migration ও reconciliation tool এখনও তৈরি করতে হবে। আগে metadata মুছে গেলে বাইরের বিশ্বস্ত evidence ছাড়া সেটি অনুমান করা যাবে না। ভবিষ্যৎ database-এর প্রকৃত engine/schema দেখে minimum reader/writer version, পুরোনো deployment-এর access-denial, constraints/transactions, schema mapping ও quota reconciliation আলাদাভাবে তৈরি করতে হবে; optional field বা শুধু advisory marker যথেষ্ট নয়। Scanner/API duplicate করার পরিকল্পনা নয়।
5. **Copy-on-write dry-run:** restored copy-তে migration একাধিকবার চালিয়ে repeatability/idempotency, upgrade ও পুরোনো-binary refusal, interrupted `RUNNING`/queued job, expiry/withdrawal, source/dataset binding, quota failures, concurrent writer, crash ও read/write compatibility পরীক্ষা করুন। Before/after count, ID-set, full-content hashes, রিপোর্ট integrity ও সব reference মিলতে হবে। Migration agent job-কে অনিয়ন্ত্রিত legacy job-এ convert করতে পারবে না। Data owner mismatch, data loss বা অমীমাংসিত reservation থাকলে থামুন। তারপরেই পৃথক approval-এ controlled cutover; implement/verify না হওয়া পর্যন্ত NO-GO।
6. **Rollback প্রক্রিয়া:** সব নতুন/পুরোনো writer ও network কাজ বন্ধ করে post-cutover data-এর আলাদা protected backup নিন। Verified pre-cutover backup আলাদা জায়গায় restore করুন; post-cutover নতুন/পরিবর্তিত job, metadata, source, reports ও quota **হারানো ছাড়া** কীভাবে reconcile/forward-migrate হবে তার অনুমোদিত পদ্ধতি আগে পরীক্ষা করুন। Agent-created record পুরোনো binary-তে expose করবেন না: lossless quarantine/archive, নিরাপদ version/permission barrier এবং পূর্ণ integrity যাচাই ছাড়া old deployment চালু নয়। শুধু পুরোনো backup বসিয়ে post-cutover writes মুছে ফেলা নিষিদ্ধ। যদি lossless reconciliation বা পুরোনো writer quarantine প্রমাণ করা না যায়, rollback বন্ধ রেখে incident escalation/forward-fix করুন।
7. **Exit criteria:** restore rehearsal ও dry-run evidence, historical ও post-cutover record/ownership/reference/quota parity, old-binary incompatibility refusal, নিরাপদ isolation এবং স্বাধীন security/operations review লিখিতভাবে গ্রহণ করতে হবে; এরপরও বাস্তব production execution-এর পৃথক explicit approval প্রয়োজন। এই checklist নিজে বাস্তব migration, অনুমোদন বা production safety-এর প্রমাণ নয়।
