# UserType capability audit — Pump 21

**Scope:** independently review the current worktree's common and profile-specific capabilities for `DEVELOPER`, `STUDENT`, `SECURITY_PROFESSIONAL`, and `PENTESTER`. This is a capability audit, not a security certification. The implementation states below come from source/contract/test/document inspection; Pump 21's full verification rerun passed, as recorded in `docs/BUILD_VERIFICATION.md`.

## State key

- **IMPLEMENTED** — the described behavior exists at that layer. It does not imply complete scanner coverage or production-grade persistence.
- **PARTIAL** — a usable bounded implementation exists, with an explicit product or infrastructure limitation.
- **NOT_IMPLEMENTED** — no implementation exists at that layer.
- **N/A** — that layer does not apply to the capability.
- Test state describes test/journey coverage present in the worktree, not whether Pump 21 has rerun it successfully. UI component tests and local HTTP integration are not browser E2E.

## Audit findings and scope decisions

1. The four UserTypes are presentation/classification values. No API authorization decision should depend on them. Role, authentication, project ownership, plan/entitlement, quota, rate limits and DAST destination policy remain distinct server-side controls.
2. The common project, source, scan, finding/lifecycle, report and assistant systems already serve all four profiles. No alternate engines or duplicate stores are warranted by this audit.
3. The Developer flow supports source snapshots and manual rescan, not Git hosting or CI/CD automation. The Student flow has finding-level explanatory guidance and progress history, not a course/classroom/grading system. The Professional flow has bounded history and project metadata, not a structured engagement-scope object. These limits are not silently filled with new speculative subsystems.
4. The Pentester target indicator means only that an owner saved a target URL. A server can validate network safety and project ownership, but this code has no independent evidence source to prove a third-party engagement contract. A client boolean would not close that gap. Keep authorization unverified and do not claim otherwise.
5. SCA vulnerability intelligence remains `NOT_ASSESSED` / `NO_DATA_LOADED`; assistant generation remains unavailable with provider `NONE`; account enable/disable is unavailable. JSON persistence and the API-hosted scan processor are not a production database or a separate worker deployment.
6. Controlled local API journeys exist for all four classifications, but no browser automation journey exists. Do not report component tests, API route tests, or synthetic DAST transport fixtures as browser E2E or public-target testing.
